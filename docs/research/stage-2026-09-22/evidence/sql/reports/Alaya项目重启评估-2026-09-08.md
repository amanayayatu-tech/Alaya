**3．最重要的缺口，是演示闭环尚未成为真实结果闭环。**

本次浏览器测试创建了一个新的复盘项目，指标是 `approved_review_gate_count >= 1`。批准首轮方向后，数据库却写入了：

```text
observation = approved_review_gate_count = 0.12
source      = mock_analytics
prediction.status = resolved
cycle.status      = closed
builder.action    = emit_task_spec + receive_mock_build_report
```

这里的 `0.12` 是第一轮演示场景的数值。新项目收到的反馈仍是“不敢点一键发布”等演示文本。知识审批以后新增的内容也来自这组演示反馈，而非这个新项目独立取得的外部结果。

源码进一步解释了现象：

- [`resolveCycleStimulus`](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/flywheel/core.ts#L577) 对前四轮使用预设场景；之后从目标草稿构造场景。
- [`scenarioFromGoalDraft`](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/flywheel/core.ts#L546) 会用 `target + 0.015 + ...` 生成观察值，并生成正面反馈、设定 `buildSuccess: true`。
- [`runBuilder`](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/flywheel/core.ts#L1070) 的任务成败来自场景字段；它产出任务规格和报告，不能据此宣称已修改软件并通过真实测试。
- [`evaluatePrediction`](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/flywheel/core.ts#L1144) 将场景值写为已解决的预测，并创建 `mock_analytics` 观察记录；[`普通推进链路`](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/flywheel/core.ts#L1640) 会调用它。

这些实现对于 mock MVP 和确定性回归是合理的。原始 PRD 也明确允许暂缓 Builder 真实改代码。真正的问题是：**如果把下一阶段目标改成真实工作收益，就必须让真实运行等待真实行动回执和外部观察，不能继续用这组场景值结算。切换真实 LLM 只改变文本生成来源，不会自动替换这些业务结果。**

已有 GitHub、表单、CSV/JSON 输入是可复用的入口，但“能导入反馈”与“反馈真正决定这一轮预测如何结算”之间，仍需在选定场景逐项接通。第一优先级应放在这里。

另外，人工控制不只是需要再验证，我在隔离副本中复现了三个确定问题：

| 入口 | 本次实际结果 | 应修复的边界 |
| --- | --- | --- |
| `PATCH /api/knowledge/:id` | 一条 `draft`、`humanApprovedCount=0`、`alpha=beta=1` 的知识，仅 PATCH `status=strong` 后返回 HTTP 200，回读仍是批准数 0 的 strong | 状态与证据不能通过普通内容编辑绕过状态机及独立审批 |
| 方向拒绝后再次 scheduler tick | reject 返回 `rejected`，下一 tick 却返回 `ran_operational_stages`，五个 Agent 留下记录，周期变成 `closed` | 拒绝与延期不能仅因为“不再 pending”就被当作允许执行 |
| `POST /api/cycles/:id/run-full` | 没调用任何独立审批接口，方向闸已经变成 `approved / approve_recommended`，产生决策记录 | 演示自动审批需要隔离身份和入口，不能成为真实运行的审批依据 |

根因可定位到具体代码：[`knowledgePatchSchema`](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/routes.ts#L130) 与[直接更新入口](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/routes.ts#L851)，[`blockingGatesResolved`](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/scheduler/core.ts#L1287)，以及 [`runFullCycle`](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/flywheel/core.ts#L1774) 调用的[场景审批函数](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/server/flywheel/core.ts#L920)。本次只证明这些本地 DEVELOPMENT 路径的行为，没有执行任何真实外部动作，也没有进行生产环境攻击验证。

这说明核心纯函数里有正确规则仍不够，所有实际入口必须使用它们。恢复真实使用前，优先修这三个入口；否则“人工闸门”无法承担项目原本赋予它的责任。默认 development 未配置 API key 时不强制认证，而服务默认监听 `0.0.0.0`，也应收敛为合适的本地访问默认值。

**4．界面已有实物，但表达比证据走得更远。**

Dashboard、人类闸门、账本、知识库、周期评审和项目设置都能加载。布局和信息量足以支撑内部操作台，无需先重做视觉设计。

有三处体验问题直接影响判断：

1. 新建项目需要先填写身份、假设、指标 key、operator、阈值、人工分钟、预算 cents 等参数。用户在获得第一项实际收益前，先承担了定义系统语义的工作。对你本人可能能用，对外部新用户的门槛明显更高。
2. 周期页把 `max(0, 1 - predictionError)` 命名为“准确率”。本次显示的 **22.6%** 实际来自 `1 - 0.7744`，不是对一组真实预测的命中率统计。[换算函数](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/client/src/lib/alaya.ts#L201)、[页面调用](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/alaya-app/client/src/pages/Review.tsx#L104)
3. “复利证据”主要展示知识引用；“已闭环”表示流程状态。引用、流程关闭、知识分数上升都可以是有用过程指标，但不能单独证明下一轮工作质量提高。

恢复时最有价值的 UI 改动，是让一个真实任务的预测、待取得的观察、已有结果、待审提案和下一步动作能被直观看懂。不要先扩展仪表盘数量。

**5．旧实验既没有证明它有效，也没有证明它必然无效。**

必须把三个问题分开：

| 实验/材料 | 实际研究问题 | 能支持的结论 |
| --- | --- | --- |
| 六月 24h 稳定基线 | 特定配置下能否完成影子运行和既定治理检查 | 归档记载 24.0146h、288 samples、8 门通过；是历史特定条件的运行证据 |
| adaptive vs disabled | MiniMax thinking 开关能否改善指标 | 24h adaptive 臂 provider/schema 稳定性失败；后续修正度量的单次对照 ECE 为 0.2012 vs 0.2067，不能形成可靠优劣判断 |
| 七月 PR-L6 | 知识注入、信用分配和选择策略是否产生学习收益 | 压缩诊断失败，正式效果没有得到有效测量；保留 FAILED / PAUSED 身份 |

来源：[24h 基线归档](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/docs/validation/2026-06-17-alaya-shadow-24h-baseline-freeze.md)、[adaptive 单次对照白皮书](https://github.com/amanayayatu-tech/Alaya/blob/7802ae20c3df5d3afd23d439291798d7796fca1e/docs/validation/WHITEPAPER_cognition_adaptive_null_result.md)、[PR-L6 失败报告](https://github.com/amanayayatu-tech/Alaya/blob/b7090b11b41f358f4d82906c86be835a68c06e64/docs/validation/PR_L6_LEARNING_LOOP_FAILED_CASE.md)。本次未重新运行这些历史实验，也未重新审计全部原始长测数据库。

PR-L6 归档里最关键的事实是：baseline 只完成 4 个可评分样本，treatment 为 0，held-out 两侧都为 0。这样的样本不能用于计算可信的学习增益。它还留下了两个治理反例：注入时的状态边界不唯一，以及事后的审批计数可能被误当成事前独立的人类授权。这些是证据有效性问题，不能通过多跑一段时间自动解决。

七月代码还有一处需要先澄清的因果链：分析器按 `predictedDecision` 与 `groundTruthDecision` 是否相同判对错，产品信用更新则从 `predictionError / worstClaimError` 生成 correct/wrong；前文的场景观察又能驱动这些误差。它们尚未证明绑定的是同一个外部 outcome。评价器认为“答对了”与系统实际给哪条知识加分，必须是一条一致的链。[评价器](https://github.com/amanayayatu-tech/Alaya/blob/b7090b11b41f358f4d82906c86be835a68c06e64/scripts/lib/health-signal-quality.mjs#L553)、[产品 credit](https://github.com/amanayayatu-tech/Alaya/blob/b7090b11b41f358f4d82906c86be835a68c06e64/alaya-app/server/knowledgeCredit.ts#L168)

**adaptive 没有显示收益，不等于知识记忆没有收益；PR-L6 无法有效评分，也不等于“经验复用”这个想法已经被证伪。** 正确判断是：核心收益主张仍待验证，同时旧验证路径暴露了真实设计问题。

**6．为什么会变得难继续：从代码演进看，验证工程逐渐超过了价值验证。**

主线有 309 个跟踪文件。按代码物理行统计，服务端约 1.83 万行、客户端约 1.01 万行、core 约 0.34 万行、测试约 1.52 万行、脚本约 0.94 万行。这个规模对单人维护已经有负担，但技术栈仍集中在 TypeScript、Express、React 和 SQLite；不是因分布式基础设施而不可挽回。

七月实验分支相对主线改了 37 个文件，新增 9,041 行、删除 103 行。对应代码分类中，服务端净增 654 行，测试和脚本净增 7,088 行。行数不是质量判据，也不意味着这些检查没有必要；它显示后期主要精力在处理试验、评分、约束、运行绑定和恢复，而非让一个真实用户更容易完成业务任务。

本地 V2 已开始针对因果顺序、审批来源、训练与留出隔离重新设计。这些方向有价值。但不可变账本、概率选择、离线策略评估、独立 evaluator 和多阶段审查的组合，本身又是一项研究工程。应保留与真实证据直接相关的原则，按本次选择的产品目标决定是否需要继续整个研究路线。

具体而言，本次独立读到 `.codex-loop/LOOP_STATE.md` 的终态为 `LOOP_BLOCKED`，M0 文档定义阶段已经完成，M1 经验账本阶段仍被阻断。修正架构审查记录保留了两个 HIGH 问题：reward 缺少完整 case/version/experiment 身份绑定，以及重复冲突的 reward 在抛错前没有留下持久化拒绝/隔离事件。当前未提交代码中的 `assertSameRun` 只核对 runId，`recordLearningLoopV2Reward` 也确实缺少 `caseId/rewardVersion`，冲突分支直接抛异常；与审查记录相符。详细的候选集、暴露内容和 propensity 被明确留待下一阶段，不能再算成同一阶段的新阻断。

本地记录显示相同阻断被连续观察三次后停止并暂停 heartbeat，后续阶段未取得接受。已有 V2 代码提供离线事件账本和信用来源记录，固定 `learnerUpdateApplied=false`，没有接入当前产品的在线 learner。要继续 V2，应先处理这两个实际合同缺陷，而不是恢复旧长跑或只修任务调度器。若本轮选择先恢复私用工具，也不必把整套 V2 研究路线都列为前置条件。

Alaya 可以继续有价值的地方，是把**一个领域里的判断、行动、结果、反例、知识变化和人工决策关联起来**，帮助你判断“这条经验现在还能不能用、究竟在哪次工作中起过作用”。本次查阅的五个官方入口没有直接替你定义这套业务语义；这不构成全市场无人竞争的证明。

因此，不建议先把 Alaya 改写到上述任何框架。现有 SQLite 和业务模型够承担第一轮验证。只有测到某个明确瓶颈，再决定是否引入替代组件。

**9．建议做一个有成本上限的恢复试验。**

首选你一个持续维护的软件项目中的“重复错误 / Bug 修复复盘”流程。输入是原始问题和当时能看到的上下文；输出是解决方案；结果由实际复现检查、测试与人工验收确认；知识记录什么改法在哪些条件下有效、在哪些条件下失败。它比“让系统学会经营一家公司”更容易取得短周期、可核验的反馈。

不建议第一轮就用股价涨跌作学习奖励。投资研究和内容表现都有反馈延迟及环境噪声，容易再次把主要工作变成搭建评分器。已有研究/内容记录可以以后接入，但这次不需要同时启动多个应用方向。

| 步骤 | 建议工作 | 结束时应看到的结果 | 粗略工作量判断 |
| --- | --- | --- | --- |
| 恢复开发基线 | 从干净主线起步，保全 V2，处理受支持 Node/依赖、时间问题及三个审批旁路 | 安装、测试、构建与审批/拒绝/提案流程一致，相关反例不能再复现 | 约 2–5 个工程工作日 |
| 接通一个真实闭环 | 复用当前模块，接行动回执和结果；真实项目不靠演示值结算 | 一次真实任务能回到原始预测、结果和知识变化 | 约 1–2 周，主要变量是结果源和既有执行工具接口 |
| 观察私用收益 | 在同一类任务里持续使用，记录人工耗时、纠错、历史引用及结果 | 你能指出具体少做了什么、避免了什么重复错误 | 2–4 周观察窗口；依任务频率而定 |

以上是按一名熟悉项目的工程师配合代码 Agent 给出的规划量级，不是已经验证的交付承诺。若第一步发现新的数据或授权边界，需调整；不包含在线学习研究、正式效果实验、SaaS 或生产部署。

第一批约 10 个真实案例用于发现操作和反馈路径问题，不能宣称统计显著。后续若要验证“会越用越好”，至少需要区分三个对照：

- A：当前惯用流程，不加 Alaya 的经验检索。
- B：相同模型和预算，使用人工审阅后冻结的简单经验清单/固定检索。
- C：相同模型和预算，使用 Alaya 基于过去结果更新的经验。

采用时间顺序，未来结果不能回流给此前决策；同一个测试案例的答案不能混进训练记忆。比较质量、重复错误和**包含录入、审批、检查、修复在内的总人工耗时**。评分尽量使用独立复现/验收，模型可以辅助整理，但不能只凭系统自述“这条知识改变了我”来给分。正式效果结论需要根据任务差异和观察到的方差另定样本量。

如果 C 优于 A、却没有优于 B，可以保留实用的账本与固定经验检索，暂不维护自适应学习。如果 B 与 C 都不优于现有流程，继续扩展没有依据。即使预测质量没有提升，只要可审计复盘显著省时，Alaya 也可以作为工作工具成立；那时应明确交付的是复盘价值。

**10．什么证据会改变本报告的建议。**

- 如果你已有一段连续的真实使用记录，显示每周总投入确实下降、历史知识改变过有外部结果支持的决策，重启优先级应上调。当前公开材料和本次检查未找到这样的证据。
- 如果真实反馈无法可靠对应到任务，或你需要花大量时间为每轮补造“可评分”结果，应停止扩展在线学习，先解决工作流本身。
- 如果简单经验清单已经达到相同效果，应保留需要的账本功能并降低系统复杂度。
- 如果你要的是一个可发表的学习系统研究项目，V2 的因果和证据工程可能值得继续；它需要单独的研究目标、资源和验收，不应计入“恢复一个私用工具”的默认工作量。

**我的建议是保留 Alaya，先投入有限的恢复和真实使用验证预算。它最有价值的资产是已经实现的可追溯工作与知识治理结构；是否继续扩大投入，由真实任务中的净收益决定。**
