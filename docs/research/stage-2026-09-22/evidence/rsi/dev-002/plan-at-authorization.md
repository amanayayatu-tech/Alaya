## 0. 先看这一页

### 结论与选择

Alaya 值得继续验证的目标是：**固定底座模型，让系统通过真实反馈改进自己的工作方法，并把改进继承到新任务。** 不承诺通用认知增强、无限进化或持续加速。

选择 **在线装箱（online bin packing）** 作为快速、客观的试验场。最终研究对象不是箱子，而是 **Alaya 的改进策略是否变得更有效**。

工作分为四段，前一段没有可用信号，后面不自动开跑：

| 阶段 | 要回答的问题 | 本阶段真实 HTTP 请求上限 | 最多能得到的结论 |
| --- | --- | ---: | --- |
| P0：最小执行环境 | 评分、隔离、调用和预算记录是否可信？ | 6 | 环境可用，不是学习有效 |
| P1：反馈搜索 | 真实反馈是否胜过同预算独立尝试？ | 120 | 反馈驱动搜索有无价值 |
| P2：一次自我改进 | 自改后的策略能否更有效地解决新任务？ | 184 | 有限领域的 Agent 自我改进信号 |
| P3：递归继承对照 | 继承后的方法是否比固定编辑方法产生更好的下一代？ | 278 | 单条谱系中的有限递归增益线索 |
| **所有阶段总计** | 条件满足才逐段执行 | **588** | 不等于开放式 RSI 已实现 |

建议资源上限：**7 个日历日、588 次真实 HTTP 请求、60 美元或等值币种的模型费用，以先到者为准。** 这是待确认的预算建议，不是现有消费授权。各阶段包括失败、重试、格式修复和反思调用；不允许另列一个不计费的“后台 Agent”。

“最大概率看到进步”的操作含义是：挑选反馈清晰、有改进空间的环境，使用可靠底座，保留完整证据，小步改变一个机制，快速淘汰无效方法。**不通过削弱基线、反复换题、增加隐形预算或挑最好的一次来制造进步。**

### 做到什么就交付

交付一个可重复运行的最小实验和一份读得懂的报告，报告必须能回答：

1. 哪一层真的出现了增益，哪一层没有测到？
2. 与什么基线相比，付出了多少调用、token、时间和费用？
3. 新任务上的效果怎样，是否只是记住旧答案？
4. 是否存在固定编辑器也能取得同样结果的解释？
5. 下一步应当保留什么、停止什么？

**可信的阴性结果也是完成；没有获得足够证据必须写“不充分”，不能改称成功或彻底不可能。**

## 1. 目标、证据层级与非目标

### 1.1 这次实际验证的命题

- H1：在相同资源上限下，读取真实历史反馈的搜索策略，优于不读取历史的独立尝试。
- H2：模型基于开发轨迹产生的新策略 v1，在新任务中从同一起始算法出发，优于原策略 v0。
- H3：让 v1 作为改进方法参与生成下一代，得到的 v2，优于继续使用固定 v0 编辑方法得到的 v2-reset；同时不能退化到不如 v1。

v0/v1/v2 是**策略版本**；本文件的 P0/P1/P2/P3 是工作阶段。实现中分别命名为 `policy_v0/v1/v2` 与 `phase0/1/2/3`，日志不得混用。

H3 即使有信号，也只是固定任务范围、固定底座、有限代数、单条改进谱系的结果。不等于基础模型权重提升，不等于普遍的学习加速，不等于无限 RSI。

### 1.2 不同“进步”不得互相替代

| 观察 | 可以说明 | 不能说明 |
| --- | --- | --- |
| 本地检查和 mock 通过 | 实现按合同运行 | 真实模型可以学习 |
| 同题修改后成绩提高 | 当前问题能被优化 | 新任务收益、RSI |
| 获胜代码在新输入上表现好 | 解法有一定泛化 | 研究方法变好了 |
| 升级策略从头搜索更有效 | Agent 方法产生可迁移增益 | 底座模型变聪明 |
| 继承编辑优于固定编辑对照 | 本次继承机制有增量线索 | 通用、持续的递归加速 |

### 1.3 本轮不做

不研究股票或金融收益；不训练大模型；不建设 Web UI、调度平台或新知识数据库；不要求先完成 G1–G7；不恢复 PR-L6、24h 长跑、PRECHECK3 或 RUN-L7；不默认开启 Distiller；不改五角色产品结构；不把实验策略写成 `strong`；不宣称优于整个 ML/RL 路线。

使用一个模型、一个顺序执行的实验程序。五角色可以保留为逻辑职责，但不得为了形式完整，把一次可以完成的请求拆成五次付费调用。

## 2. 为什么这条路线值得试，以及不能承诺什么

### 2.1 外部证据的正确用法

- DGM 报告了 Agent 修改自身代码/流程后的基准提升，也记录了伪造工具结果和规避检测的失败。支持“有限自我改进值得测”，不证明任意实现都有效。[原始介绍](https://sakana.ai/dgm/)
- GEPA 通过执行轨迹反思和提示更新获得任务提升。支持固定权重下的方法改进，不等于无界 RSI。[论文](https://arxiv.org/abs/2507.19457)
- ACE 研究可积累的上下文经验，也指出反复摘要可能丢失细节。支持保留证据和检验经验组织方式，不支持默认蒸馏总是更好。[论文](https://arxiv.org/abs/2510.04618)
- FunSearch 在在线装箱上使用“提出程序—执行评分”的搜索取得改进。它是试验场选择的依据，不是 Alaya 已有效的依据。[原始介绍](https://deepmind.google/discover/blog/funsearch-making-new-discoveries-in-mathematical-sciences-using-large-language-models/)
- OpenAI 公开区分 AI 辅助研究加速和完全自主的递归自我改进。不能把行业方向当成项目验收结果。[公开说明](https://openai.com/index/ai-policy-window/)、[研究加速观察](https://openai.com/index/research-acceleration-view-inside-openai/)

以上是截至 2026-09-22 查阅的作者/机构公开材料，不是本项目独立复现。

### 2.2 对 Alaya 既有结果的处理

- SQL 旧实验：原始经验 24/24、蒸馏经验 22/24；不能默认蒸馏优于直接经验。
- 后续 SQL probe 没有进入完整 A/B，不得把它说成已经否定全部经验迁移。
- M1/M1.1 的候选和调用契约问题，不能直接解释为 RSI 无效。
- 原有长测、模拟与账本是可复用的工程资产，但不能代替本文件中的新对照。

原始回执：[SQL 收口](../Codex/2026-09-13/codex-threads-01a0815b-e691-7f81-9073/outputs/alaya-sql-closeout-20260913.md)。旧结果不回写、不重新命名成新实验结果。

### 2.3 为什么不先做模型训练

autoresearch 的固定约 5 分钟训练循环，更接近模型研发，但原版要求 NVIDIA GPU；不保证在本机上同样工作。AI4AI-Bench 对训练算法的研究也需要小时级研发和后续训练重跑。先用 CPU 可评价的程序搜索，减少硬件与训练随机性的干扰。[autoresearch](https://github.com/karpathy/autoresearch)、[AI4AI-Bench](https://arxiv.org/abs/2608.20318)

若未来转向训练层，必须另外证明“改进后的模型更会产生下一代”，不能只展示验证损失下降。本轮不安装这些框架。

## 4. 实验环境合同

### 4.1 装箱任务

- 箱子容量固定 100；物品为 1–99 的正整数；每条序列 256 个物品。
- 在线决策：候选只能接收当前物品和当前已有箱子的剩余容量，不能读取未来物品、随机种子或评测文件。
- 候选输出一个已有箱子索引，或显式的 `NEW_BIN`。
- 选中容量不足的箱子、非法索引、非有限数、异常、超时，均是非法候选；不能静默改成合法选择。
- 主机端独立更新箱子状态并核对每件物品恰好装入一次，不能使用候选自报的箱数。
- 分数为箱数，越少越好。所有实例必须合法；非法候选不能成为冠军。
- 每次搜索从同一份可运行 Best Fit 开始；保留它作为安全冠军。First Fit 只作环境基线，不把打败它当主要成功。

接口建议为 JavaScript 的 `chooseBin(item, remainingCapacities)`。代码输出合同统一为 JSON 根对象中的 `code` 字符串及简短 `hypothesis`；父子策略输出合同统一为根对象中的 `policy` 字符串及 `change_reason`。不使用任意补丁修改宿主仓库。

### 4.2 数据分布：实现时照表生成，不看结果后改题

表中区间均为包含端点的整数均匀分布，概率选择均独立，除非明确标为分块。所有序列长度相同。

| 用途 | 世界 | 固定分布 |
| --- | --- | --- |
| P1 开发 | D1 | U[1,99] |
| P1 开发 | D2 | 50% U[5,35]，50% U[65,95] |
| P1 开发 | D3 | 70% U[10,40]，30% U[60,90] |
| P2 新任务 | T1 | 25% U[5,40]，75% U[60,95] |
| P2 新任务 | T2 | 20% U[1,20]，50% U[40,60]，30% U[80,99] |
| P2 新任务 | T3 | 前 128 件 U[51,79]，后 128 件 U[21,49] |
| P3 新任务 | R1 | 60% U[10,45]，40% U[55,90] |
| P3 新任务 | R2 | U[25,75] |
| P3 新任务 | R3 | 前 128 件 U[1,49]，后 128 件 U[51,99] |

这些是不同任务分布，不是不同现实业务领域。报告不得夸成跨领域通用能力。

每个“世界 × 独立重复”生成 `train=32、dev=32、test=128` 条不同序列。同一配对内，各策略使用完全相同的数据；不同重复使用独立种子。P1 每次搜索在 D1–D3 的等权组合上优化；P2/P3 每个世界分别从头搜索。

### 4.3 不泄漏的反馈

- `train`：可向模型提供分布统计、训练成绩和最多两条训练反例/决策轨迹。
- `dev`：宿主用于在候选之间选冠军；**不将 dev 成绩、实例或轨迹回传给候选生成模型**。
- `test`：冠军与策略版本冻结后才评分；不用于挑策略、挑候选、写经验、改提示或筛选世界。
- 数据生成器、种子和 test 文件只在可信宿主中；候选容器和模型请求都不获得这些文件。
- 保存全部种子和数据哈希以供复现。相同序列跨 split 去重后重新生成；不靠重命名制造“新题”。

P1 的 test 结果只决定是否继续；产生 policy_v1 的请求只能使用 P1 的训练轨迹和原策略。P2 test 不进入下一代编辑请求；产生 policy_v2 只使用 P2 的训练轨迹。执行者也不得根据 test 错题手写策略。

## 5. 可信执行、模型与预算

### 5.1 隔离必须是真的，但不自研安全框架

优先使用本机现有容器运行时。候选进程无网络、无凭证、非 root、只读根文件系统，限制 CPU、内存、进程数和时间；仅挂载当前候选和必要 worker，不挂仓库、用户目录、Docker socket、协议或评测数据。

可信宿主逐步传入当前决策所需的数据，自己保管剩余序列和评分。不要把完整序列交给候选后仅靠提示词要求“别偷看”。可批量处理不同实例当前时刻的输入以降低 IPC 开销，但不得传入未来时刻。

Node `vm`、提示词禁止项或 subprocess timeout **单独都不构成隔离边界**。已有隔离不可用时，先完成其余离线工作并报告；不能悄悄降级为在宿主直接执行生成代码，也不另造大型沙箱。

候选每条序列从清洁执行状态开始，不在测试实例间继承隐式全局状态。资源默认值：单个 worker 1 CPU、256 MiB 内存、最多 64 进程、64 MiB 临时空间；单批候选评分最多 30 秒，超时记失败。P0 测量实际开销，不把简单基线的毫秒计时当成完整隔离评分延迟。资源值可以在不接触 test、不运行正式对照的离线预检中按实际环境修正，之后记入协议并对所有组冻结。

### 5.2 模型选择

默认复用用户已有、已授权的 Alaya OpenAI-compatible 配置；记录真实 provider、model ID、版本标识（若有）、参数和 endpoint 主机名。**不默认采用代码中的老型号 fallback，也不自动切换付费平台。** 历史使用 MiniMax-M3 不代表现在仍可用。

P0 使用代表性代码生成/修正请求检查现有模型是否能遵守合同。成功后冻结型号及推理设置，后续各组一致。若现有模型不能可靠产生合法代码，结论是本底座/接口尚未就绪；将“换一个更强且可用的模型”作为明确的新选择，不用增加无效重试掩盖。

建议 `temperature=0.7`；若模型不支持则使用其支持的固定设置，并对所有组一致记录。调用输入、输出与推理 token 均计入资源。模型变更构成新实验版本，旧结果不可混合。

### 5.3 必须补到真实入口的最小问题

现有 provider 有自动重试和简化 schema fallback；**`maxRetries=0` 不意味着最多一次 HTTP 请求**。当前 `retryCount + 1` 也不能作为权威请求计数。现有 `estimatedCost` 使用启发式费率，不能充当硬预算账本。

执行者必须在实际 HTTP 边界实现/复用：

1. 请求前预留调用和最大费用；所有自动重试、fallback 都占预算。
2. 记录实际 HTTP 次数、模型返回的 usage、finish reason、延迟、脱敏响应和错误。
3. 严格解析完整 JSON 根对象；不把截断返回中的内层对象视为根对象。
4. `degradedToHumanGate`、schema 错误、合法但无候选、传输失败分别记录；不能作为有效候选。
5. 使用执行时核实的官方价格及其日期估算费用，并以实际 usage 回填；缺 usage 时按预留上界保守计费，不能记零。无法建立可信费用上界则不启动付费段。

优先复用现有 transport；如果需要调整共享 provider，仅在隔离工作树增加最小可测的预算/记录入口，默认产品行为保持不变。检查所有调用方，用假 HTTP 回归实际 `LLMProvider.call()` 入口。不把全套 M1 修复列为本实验的前置任务。

### 5.4 硬预算口径

- 总上限：588 次实际 HTTP 请求与 60 美元，先到即停；账本在整个实验中累计，不按新进程重置。
- 生成请求：每次输入不超过 8,000 token、输出上限 3,000 token；更新策略的请求也遵守相同上限。若 provider 有额外收费项，将其纳入预留。
- P1 每条搜索轨迹最多 20 次实际 HTTP 请求；P2/P3 每条最多 10 次。反思或修复占同一上限，不能额外调用。
- 固定每条轨迹的输入/输出 token 总上限分别为请求数 × 上述上限；记录实际消耗与成绩—消耗曲线，不为了凑齐 token 填充无意义文本。
- 费用若预计不足以覆盖下一整阶段，先报告预计可完成范围及选择，不能跑半个对照后宣称赢了。
- 每次搜索至多评估相同数量的候选；一个请求返回多个候选只接受合同约定的一个，不能隐藏 best-of-N。
- 系统不稳定触发连续 3 次基础设施错误时停止该阶段并诊断；已耗预算保留。模型提出的非法算法属于任务失败，不冒充基础设施错误删除。

### 6.2 policy_v0 的固定起点

以下内容作为基础工作方法，不随实验成绩手工增强：

> 你在固定资源内优化在线装箱策略。每次返回一份完整候选代码和一个简短、可检验的改进假设。遵守在线输入和合法输出合同。若获得历史反馈，结合当前冠军及最近的真实失败，选择一个有根据的修改；无可靠改进时可以保留现有方法。不得声称未执行的测试通过，不得请求改变评分、数据或资源上限。需要修改你自己的工作方法时，也依据实际轨迹提出一份有限修改，不添加工具权限或改变目标。

任务说明、代码输出合同、预算和数据访问限制属于不可变系统部分，不由可进化策略重复定义。

### 6.3 最小充分离线检查

- 手算小例子与独立宿主箱数一致；Best Fit/First Fit 合法且可复现。
- 在 train/dev 上报告 Best Fit 与 `ceil(物品总大小 / 100)` 容量下界的差距，先确认有可测余量；该下界不一定可达到，有差距也不保证能改进。若全部开发实例已达到下界，不花 120 次请求验证一个没有分辨力的环境，标记 `NO_MEASURABLE_HEADROOM` 并给用户看开发数据，不偷偷削弱基线或查看 test 后换题。
- 同种子复现，不同 split 无重复；train/dev/test 的读取边界走真实 runner 检查。
- 非法索引、容量超限、异常和超时不会成为冠军；失败后保留合法起点而非伪造成绩。
- 候选不能读取未来输入、评测文件或凭证，不能联网；不能写宿主文件。
- 假 HTTP 覆盖合法根对象、截断 JSON、schema 失败、fallback/重试实际计数、缺 usage、预算即将耗尽。
- 整个付费实验用 mock 跑一次，包含 continue/stop 分支和从磁盘独立重算报告。

不额外构造大规模 fuzz 平台；只有相关失败才扩覆盖。若改共享 provider，运行已有 provider 回归与相关类型检查；未改 Web/数据库，不启动整套产品长测。

### 6.4 最多 6 次真实请求

仅在用户已明确授权付费执行、费用预检通过后进行：两次代表性代码生成、两次根据真实错误修正，最多两次用于必要的接口诊断。一次 provider 调用可能包含多次 HTTP，累计最多 6。

就绪条件：至少一份合法代码、一次真实反馈后的合法修正、预算账本与 HTTP 回执对应、完整结果可重放。它不要求成绩提高，不构成 H1 通过。

数据或费用不可信：`INVALID_MEASUREMENT`；模型/接口未就绪：`BLOCKED_RUNTIME`。先报告具体失败，不能把这些记作学习阴性。

## 7. P1：先确认真实反馈有用

### 7.1 两组与公平性

- `independent`：每个请求只得到固定任务说明、Best Fit 起点和同样的训练数据概况；不获得先前候选或成绩。宿主保留全部候选并用 dev 选冠军。
- `feedback_v0`：相同基础输入，另给当前训练冠军、最近最多 4 条原始尝试摘要及最多 2 条训练反例；由 policy_v0 指导修改。不调用 Distiller。

原始摘要只截取确定字段，不由另一模型编写。始终保留候选代码和完整原始回执；摘要太长时按固定次序截断，不能按人类判断只保留有利证据。

两组每次都从同一个 Best Fit 起点开始；各 3 次独立重复；每条轨迹最多 20 次真实请求，总计 120。交错组间执行顺序，降低 provider 随时间变化的影响。配对的是相同任务数据和预算，不声称模型随机数完全配对。

每次最后在全部合法候选与初始 Best Fit 中，以 dev 平均箱数选一个；并列时优先代码较短、再按生成顺序选。选择规则对各组一致，test 不参与。

### 7.2 是否继续

定义每个配对的相对改善率：

`gain = (control_mean_bins - treatment_mean_bins) / control_mean_bins × 100%`

这里 control 是独立尝试，treatment 是反馈搜索；均是 test 上的等权平均箱数。

筛查继续条件：3 次配对的平均 gain ≥ 0.5%，至少 2 次为正，并且反馈组平均成绩确实优于共同的 Best Fit 起点。0.5% 是本版事先选定的最低实用差异，不是自然定律，不得看完 test 后下调。

- 满足：`FEEDBACK_SEARCH_PROMISING`，允许进入 P2，但不称为稳健统计证明。
- 未满足且测量有效：`NO_PRACTICAL_FEEDBACK_GAIN`，本轮停止付费扩展，报告反馈是否真正改变提案及主要失败原因。
- 若 train/dev 也完全无可改进空间：报告本任务/搜索空间缺乏分辨力，不在当前运行中临时换分布后续接成绩。

主指标未过时，不以“某个最好候选很漂亮”放行。环境正确但模型表现差时，也不能通过人工给反馈组额外提示补救。

## 8. P2：一次自我修改能否迁移？

### 8.1 生成 policy_v1

仅使用 P1 的开发训练轨迹、policy_v0 和不可变合同。轨迹选择采用固定规则：每次反馈搜索轨迹的首个候选、训练冠军、最后一个候选，以及按训练损失排序最差的一个合法候选；去重后按时间排列。不要读取 test 错题。

让 policy_v0 作为当前工作方法指导同一个模型，输出一份新的研究策略。只允许修改“怎样使用反馈、形成假设和选择下一次改动”的自然语言工作方法。

最多 4 次真实请求，只接收**第一份合法策略**；后续请求只允许修复输出格式或越界内容，不按效果挑多个版本。无合法策略即 `NO_VALID_POLICY_UPDATE`。

策略总长上限 6,000 字符；禁止嵌入可直接执行的完整装箱解法、测试数据/种子、改变预算或放宽限制。保留完整 policy_v0/v1、diff、编辑请求和 lineage。自然语言可以包含方法性经验；因此成功也不代表消除了所有领域先验。

### 8.2 从同一起点比较

- 比较 `feedback_v0` 与 `feedback_v1`。
- 分别在 T1–T3 上做 3 次独立重复：2 个策略 × 3 世界 × 3 重复 × 10 请求 = 180。
- 每条轨迹都清空此前候选、获胜代码、训练实例和局部状态，从相同 Best Fit 开始。
- 两个策略都获得当前新任务的同种反馈、相同上下文上限和同样的候选选择器。唯一有意变化是冻结的策略文本。
- 搜索期间不继续修改策略；不让 v1 携带旧解法而 v0 没有。

本阶段上限 4 + 180 = 184 次请求。

### 8.3 继续条件与表述

按第 10 节的 9 个配对分析。若达到“实用信号”条件，标 `SELF_MODIFICATION_PROMISING` 并允许 P3；若同时满足不确定性条件，可写“本任务范围内有支持证据”。否则写 `NO_PRACTICAL_SELF_MODIFICATION_GAIN` 或 `INCONCLUSIVE` 并停止扩展。

本阶段已经回答一个有价值的问题：现有模型能否通过改写自己的方法，改善新的搜索过程。即使阳性，它仍可能是一次有效的提示优化，不独自证明递归继承的必要性。

## 9. P3：不能少掉的固定编辑方法对照

### 9.1 产生两个下一代

两个编辑分支获得**完全相同的 policy_v1 源文本、P2 训练轨迹和任务合同**；使用同一模型、参数、输入长度规则及最多 4 次真实请求。P2 训练轨迹按第 8.1 节的确定规则选取，只取 policy_v1 的训练记录；若超出输入上限，按世界、重复、时间轮转取样并记录截断位置，两个分支使用同一份材料：

- `inherited_editor`：使用 policy_v1 作为当前改进工作方法，编辑 policy_v1，产生 policy_v2。
- `reset_editor`：使用固定 policy_v0 作为当前改进工作方法，也编辑同一份 policy_v1，产生 policy_v2_reset。

两个分支的差别仅在“执行编辑的工作方法”；不能让 reset 分支少看轨迹、少看源文本或少用预算。都接收第一份合法输出，不根据下游测试选择一个好看的 child。

必须记录编辑时实际注入的策略全文与哈希。仅给产物起名“v2”但仍用相同固定编辑方法，不算递归继承。

### 9.2 比较继承是否有额外价值

在全新的 R1–R3 上比较 policy_v1、policy_v2、policy_v2_reset；每世界 3 次独立重复，每条 10 请求：3 × 3 × 3 × 10 = 270。

与 P2 一样，全部从 Best Fit 清洁起点开始，只继承策略。编辑 8 + 评测 270 = 278 请求。

主要比较是 `v2 vs v2_reset`；同时检查 `v2 vs v1`，不能以“比另一个失败 child 好”掩盖相对亲代退步。

- v2 胜 v1，也胜 v2_reset：报告 `BOUNDED_RECURSIVE_SIGNAL`，即本次有限继承机制有增量线索。
- v2 胜 v1，但不胜 v2_reset：报告 `ITERATIVE_OPTIMIZATION_ONLY`；可以保留有效改进，但递归方法尚无额外证据。
- v2 不胜 v1：报告 `NO_NEXT_GENERATION_GAIN`，保留亲代，不自动进行 v3。
- 结果不稳定：报告 `INCONCLUSIVE`，不得宣称“递归越跑越强”。

这是**一条策略改进谱系**。9 次下游搜索重复不等于 9 次独立的策略进化实验。即使全部有利，也不宣称跨谱系稳健；是否另外复现独立谱系，在本轮报告后由用户决定，不偷偷追加本轮预算。

## 10. 分析、阈值与结论规则

### 10.1 主指标

每条搜索轨迹的主指标：**在固定资源上限内，由 dev 选出的最终算法，在 test 上的平均箱数**。不分析测试集挑出的最优候选。

P2/P3 将 3 世界 × 3 重复得到的 9 个配对 gain 等权平均。不同世界不能因测试实例多而获得更大权重。报告所有配对值、各世界均值和整体均值。

“实用信号”的固定定义：整体平均 gain ≥ 0.5%，至少 6/9 个配对为正，且任何世界的平均退化不超过 0.5%。零差异不是正向。

P3 的两个必要比较分别应用该规则。禁止挑一个比较成功就概括为全部成功。

### 10.2 不确定性

用配对搜索运行作为抽样单位，按世界分层做 10,000 次 bootstrap，保存分析 seed，给出区间。P2 报 95% 区间；P3 对两项必要比较各报 97.5% 区间，用保守的双比较处理。

- 达到实用条件但区间仍跨 0：只称“有希望”，不称稳定成立。
- 达到实用条件且对应区间下界 > 0：可以称该实验范围内有支持证据，仍保留样本少和单谱系限制。
- 无实用改善、区间跨 0：区分“当前预算没看到”与“不可能存在效果”。

小样本 bootstrap 也有局限，不能包装成正式科学结论。不按数万件物品或上千测试序列虚增独立样本数。不反复看显著性后决定是否加跑。

### 10.3 成本与失败

同时报告实际请求数、输入/输出/推理 token、provider 错误、候选非法率、评分时间与总费用。学习策略的生成成本单列并计入总成本；不能只展示部署后每次任务更便宜。

预算硬上限或基础设施问题使配对未完成：标 `PARTIAL`，保留全部失败和消费，不用缺失的一组当零分宣布另一组胜出。

合法起始 Best Fit 可以作为所有无改进轨迹的最终结果；这是明确的算法保底，不能把候选失败擦掉。若冠军在任一 test 序列上非法，该轨迹标记 `INVALID_CHAMPION`，主指标按 256 箱计入（逐物品新开一箱的最差合法上界），不得删除这条配对。另行展示部署时回退 Best Fit 的成绩，不能混入主指标掩盖非法率。若双方均为非法冠军，则两者 gain 为 0，仍分别报告失败。

完成时由执行者重新读取落盘文件，校验 hash、实际 HTTP 总数、每组资源上限、测试选择边界，并重新执行分析。独立回读指不依赖模型自述，**不要求引入新的 Reviewer 或子代理门槛**。

报告第一页固定包含：

1. `DEVELOPMENT` 与实际完成阶段。
2. H1/H2/H3 分别为支持线索、无实用增益、未验证或测量无效。
3. 全部组的成绩和成本，不只展示冠军。
4. 一句因果解释，并标明仍存替代解释。
5. 一个下一步动作；如果没有证据支持继续，就明确停止该方法。
