# Alaya 实现方案与架构评审

评审对象：Alaya PRD v0.2（2026-06-03）
评审目的：在动手写代码前，审慎判断"能不能做、值不值做、怎么做最稳"，并暴露 PRD 中需要在实现前补齐的规格漏洞。
约定前提：第一版全程 mock LLM，交付可在本地运行的完整项目。

---

## 0. 一句话结论

> 这个项目**工程上做得出来，而且 PRD 已经做完了最难的产品决策**；真正的风险不在能不能跑，而在跑起来后飞轮是否产生真实复利。在动手前，有 8 个规格漏洞必须先定死，否则会把"模糊规格"变成"代码里的隐性 bug"。

PRD 的成熟度高于大多数同类设计文档——它把技术栈、置信度计算、误差公式、状态机、闸门预算都锁死了，且 22 章主动列出了自己的"无法根治点"。这是清醒的。但清醒不等于无漏洞。

---

## 1. PRD 漏洞清单（实现前必须定死）

下面每一条都是我用代码验算或交叉比对 PRD 章节后确认的，不是主观挑剔。按严重程度排序。

### 漏洞 A —— compute_error 无法处理"越小越好"指标【严重 / 会算错误差】

10.5 的公式 `e = clip(max(0, d*(T-O))/s, 0, 1)` 只给了"达标方向 d=+1"，但没说"越小越好"类指标（如 bug_rate <= 0.05、churn <= 0.1）怎么设 d。

验算：目标 bug_rate <= 0.05，实际 0.02（明明达标），若按 d=+1 算出误差 = **0.6**——系统会把一次成功的 Bug 收敛误判为预测失败，进而错误地给知识 `beta += 1`，污染置信度。

**修复要求**：claim 必须显式带 `operator`（>= 或 <=），由 operator 推导 d：`>=` 时 d=+1，`<=` 时 d=-1。compute_error 的输入应是 `(target, observed, operator, scale)`，而不是让上游手填 d。

### 漏洞 B —— compute_error 在 T=0 时除零【严重 / 会崩溃】

10.5 说 `s 默认取目标值或历史标准差`。当目标值 T=0（例如"崩溃数=0""未处理工单=0"这类绝对目标），s=T=0 → 除零。

**修复要求**：scale 必须有正下限（如 `s = max(target, eps)` 或强制使用历史标准差），且在 claim schema 层禁止 scale=0。

### 漏洞 C —— E_cycle 平方加权未达到"惩罚大错"的设计意图【中等 / 误导决策】

10.5 声称"使用平方误差是为了惩罚少数大错"。验算结果相反：

- 9 个小错(e=0.1) + 1 个完全失败(e=1.0)
- 平方加权 E_cycle = **0.109**
- 线性平均 = **0.19**

平方版本反而更低。因为平方把小错(0.1²=0.01)压没了，而那个关键的大错被 10 个等权项稀释。结果是系统**鼓励用大量低价值小预测淹没一个关键失败**——与设计意图完全反向。

**修复要求**：三选一——(1) 给关键 claim 显著更高的 weight（PRD 已留 weight 字段，但需要强制 metric_threshold 关键预测 weight≥3）；(2) 改用 max 而非加权平均来捕捉"最差预测"；(3) E_cycle 同时输出 `worst_claim_error`，让 18.3 的"连续 2 轮 E_cycle 超阈值"判定不被稀释掩盖。建议同时做 (1)+(3)。

### 漏洞 D —— evidence_count 定义不自洽【中等 / 状态机错误迁移】

8.5 示例里 `alpha=2, beta=1` 但 `evidence_count=1`；8.6 初值 `alpha=1, beta=1`。那么 evidence_count 到底等于什么？

- 若 `evidence_count = alpha + beta - 2`（减去 Beta 先验），则示例自洽（2+1-2=1）。
- 但 PRD 从未写出这个公式。

这直接影响所有状态迁移判定（draft→active 需 evidence_count>=1，active→strong 需 >=5）。定义错了，整个知识晋级链路就错了。

**修复要求**：明确写死 `evidence_count = (alpha-1) + (beta-1)`，即剔除先验后的真实证据条数。所有迁移规则统一用这个口径。

### 漏洞 E —— 灰区死锁，strong 知识可能永远无法晋级【严重 / 飞轮复利失效】

8.6 证据规则：误差 e<=0.3 才 alpha+=1，e>=0.7 才 beta+=1，**0.3~0.7 灰区不累加**。真实产品反馈大量落在灰区。后果：evidence_count 长期不增长 → 知识卡在 draft/active → 永远到不了 strong → 17.3 飞轮验收要求的"第 3 轮引用前两轮知识改变决策"无法达成 → **飞轮看起来在转，但不产生复利**（正好命中 22.2 的"飞轮空转"）。

**修复要求**：(1) 为灰区设计弱累加（如 e∈[0.3,0.5) 给 alpha+=0.5）或引入"连续 N 次灰区"触发人类意义闸的规则；(2) 把"人类批准 alpha+=3、外部验证 alpha+=2"作为灰区指标的主要晋级通道，并在 onboarding 就让用户理解前 3 轮主要靠人类喂证据（PRD 22.3.5 已承认这点，但算法层没有对应机制）。

### 漏洞 F —— 知识衰减函数完全缺失【中等 / stale 无法自动触发】

8.6 写"衰减后 confidence_score<0.5 → stale"，但全文没有衰减公式、衰减触发周期、衰减速率。没有它，active→stale 这条迁移在代码里无法实现。

**修复要求**：定义显式衰减，如 `score_decayed = score * exp(-λ * days_since_last_validated)`，并给 λ 和 stale 检查周期默认值（建议按 cycle 触发，而非按天，避免后台定时任务）。

### 漏洞 G —— directional/binary/categorical claim 不进入 E_cycle【中等 / 误差信号不完整】

10.5 的 E_cycle 公式只对 metric_threshold 的连续 e 定义清楚。但 10.4 表里 binary/categorical/directional 也产出 0/1/0.5 的离散误差。它们要不要进 E_cycle 的加权平均？权重怎么定？PRD 没说。

**修复要求**：明确 E_cycle 纳入所有"可自动计算"的 claim 类型（metric_threshold + binary + categorical + directional），qualitative 排除。离散误差直接作为 e_i 参与平方加权。

### 漏洞 H —— 字段级写权限的执行机制未定义【中等 / 并发设计落不了地】

12.2 要求"Agent 只能写自己有权限的字段""任务级锁""乐观并发控制"。这是正确的设计方向，但 PRD 没给出：哪个 Agent 能写哪些字段的权限矩阵；version 冲突时的重试/回滚策略；任务级锁的粒度（按 task_id？按 cycle_id？）。

**修复要求**：实现前先产出一张"Agent × 表 × 字段"的写权限矩阵。这是 22.3.4（多 Agent 协同复杂度）唯一能在第一版兜住的工程手段，不能省。

## 2. 架构评审（PRD 选型基本正确，少量加固）

| 维度 | PRD 选择 | 评审意见 |
|---|---|---|
| 技术栈 | Next.js + TS + SQLite + FTS5 + OpenAI | 正确。锁死不摇摆这条纪律（5 章）尤其值得保留。 |
| 状态存储 | SQLite + version 列 + event_log | 正确。乐观锁 + event_log 是多 Agent 一致性的最低可行方案。建议 event_log 用 append-only，且记录 before/after 字段快照以支持 22.4 的 "event replay" 测试。 |
| 检索 | FTS5 关键词优先，向量延后 | 正确。MVP 阶段知识量小，FTS5 + 状态过滤足够，过早上向量库是浪费。 |
| Agent 运行时 | 后端内顺序调度，不上并发框架 | 正确。顺序调度让 event_log 天然有序，调试和回放都简单。 |
| LLM 层 | OpenAI 占位 + 可切换 | 正确，但**第一版全程 mock**（你的选择）反而更优：用确定性假 LLM 跑通飞轮逻辑，把"飞轮是否复利"和"LLM 质量好不好"两个变量解耦，先验证前者。 |

**唯一架构建议**：把所有 LLM 调用抽象成一个 `LLMProvider` 接口，mock 实现返回固定/可配置的结构化 JSON。这样切真实 API 时零改动业务逻辑，也让 16.1 的 schema 校验/retry/降级逻辑可以用 mock 注入故障来单测。

## 3. 建议的实现里程碑（基于"先验证内核"原则）

PRD 的 Phase 0.5 是整个项目性价比最高、也是最便宜的"证伪点"。建议严格按此推进：

### M1 —— 数值内核 + 单元测试（最高优先，先做）
- 修复漏洞 A/B/C/D/E/F/G 后实现四个纯函数：`compute_error`、`classify_error`、`update_confidence`、`transition_knowledge_state`。
- 每个函数配边界测试（达标、超额、灰区、除零、越小越好指标、人类批准晋级）。
- **退出标准**：所有边界用例通过，且漏洞清单 8 条全部有对应测试覆盖。

### M2 —— 数据层 + event_log + 写权限矩阵
- SQLite schema（13.2 的 11 张核心表）、version 列、乐观锁、Agent×字段写权限矩阵。
- event_log append-only + before/after 快照。
- **退出标准**：并发写同一行触发 version 冲突能正确重试/拒绝；event replay 能重建任意时刻状态。

### M3 —— 5 Agent 顺序调度 mock + 3 轮飞轮数值模拟
- 五个 Agent 以 mock/adapter 形态跑完整飞轮（PRD 强调不得砍成单 Agent）。
- 用确定性假数据跑 17.3 的 3 轮飞轮。
- **退出标准（这是真正的项目生死线）**：第 3 轮建议能明确引用前两轮知识，**并说明该知识如何改变了建议**（不是只贴 ID）；不重复已否决方向；pending_human 不无限膨胀；5 个 Agent 每轮都有运行记录。

### M4 —— 后端 API + 前端 5 页面
- 15 章的 CRUD API；14 章的 Dashboard / Human Gates / Prediction Ledger / Knowledge Base / Cycle Review。
- gate budget、意义闸合并、安全模式（11.4 / 18.3）。

### M5 —— LLM 接入（mock→真实可切换）
- LLMProvider 接口 + schema 校验 + retry + 降级 + 调用日志 + 成本统计（16.1）。
- 此时才接真实 OpenAI，因为前面已确认飞轮逻辑本身成立。

**关键纪律**：如果 M3 的退出标准达不到（飞轮不复利），不要前进到 M4/M5。这是 PRD 22.5"必须设置的失败阈值"的工程化体现——宁可在数值模拟阶段证伪，也不要做完漂亮前端才发现飞轮空转。

## 4. 对 6 个"无法根治点"的实现期判断

PRD 22.3 诚实地列了六个结构性难题。我的判断是：**它们都不该阻止第一版开工，但每一个都需要在第一版就埋下"承认局限"的机制**，而不是假装能解决。

| 无法根治点 | 第一版能做的 | 第一版做不到的（要诚实承认） |
|---|---|---|
| 22.3.1 隐性知识捕获不全 | 记录人类裁决上下文、founder_preference_trace；涉及创始人偏好默认升级意义闸 | 真正"理解"创始人。系统必须能主动说"我不确定"。 |
| 22.3.2 价值误差难自动检测 | 检测"指标达标但人类否决""与 identity 冲突" | 自动判断方向是否值得继续。这永远需要人类责任主体。 |
| 22.3.3 反馈无干净奖励函数 | 保留用户原话、聚类、灰区进意义闸 | 把模糊反馈自动闭环。learning signal 必须过人类。 |
| 22.3.4 多 Agent 复杂度上升 | 字段级写权限 + event_log + 顺序调度 | 让边界永不模糊。协调成本是长期的。 |
| 22.3.5 2-3 小时预算可能不够 | gate budget、合并、抽样降级 | 保证前 3 轮就省时间。前 3 轮是投入期不是回报期。 |
| 22.3.6 做成了却不值得做 | 坚持"私有杠杆"定位，不急于 SaaS | 解决"通用 vs 针对性"的结构张力。 |

**结论**：这六点不是开工的阻碍，而是验收时的"诚实标尺"。第一版的成功 = 飞轮能跑 + 数值模拟显示复利，而**不是**解决了这六个难题。

## 5. 给你的最终建议

1. **先做 M1+M3（数值内核 + 3 轮模拟），全程 mock LLM。** 这是最便宜的证伪点，几天就能给你"飞轮到底转不转"的真实信号。在确认复利之前，不值得投入 M4 前端。

2. **开工前花半天把第 1 章 8 个漏洞定死。** 尤其 A（越小越好指标）和 E（灰区死锁）——这两个直接决定误差算得对不对、知识能不能晋级，是飞轮复利的命门。我可以直接把修复后的算法规格写成代码。

3. **把"承认局限"做进系统，而不是等它失败。** 第一版就要让 Agent 能输出"我不知道，需要人类判断"（21 章成功标准的最后一条）。这比多写几个 Agent 能力更重要。

4. **守住失败阈值（22.5）。** 把那 8 条阈值做成 Dashboard 上的可见指标，触发即暂停扩张、回到架构修正。这是防止"做了一堆功能但飞轮空转"的唯一纪律。
